# Test Ideas: Secure Document Upload Feature

## Overview
This document outlines test ideas and risk-focused testing scenarios for the Secure Document Upload feature intended for paralegals. 

### User Story
> As a paralegal, in order to store and share legal documents, I want to be able to securely upload documents.

### Acceptance Criteria
* Upload should support the following common file formats: `PDF`, `DOCX`, `TXT`.
* The maximum file size should be **20MB**.
* When a document is uploaded it should give a progress update to the user.
* Once uploaded, the document must initially be only accessible to the person who has uploaded it.
* A report of the upload and whether it was successful or not will be stored in the auditing feature.

---

## 1. Functionality & Progress Reporting

| Test ID | Scenario Description | Expected Outcome | Risk Focus |
| :--- | :--- | :--- | :--- |
| **FUNC-01** | Upload standard valid `.pdf`, `.docx`, and `.txt` files | File uploads successfully, displays in list, and is previewable/downloadable. | Core Functionality |
| **FUNC-02** | Upload unsupported file formats (e.g., `.exe`, `.png`, `.zip`, `.pages`, `.doc`) | System rejects the file immediately with a clear, user-friendly error message. | Input Validation |
| **FUNC-03** | Progress bar accuracy during standard upload | Progress bar smoothly updates from 0% to 100% reflecting actual byte upload state. | UX / Transparency |
| **FUNC-04** | Progress update under degraded network conditions (throttled 3G) | Progress indicator accurately reflects slower speed without timing out prematurely or freezing. | Resilience |
| **FUNC-05** | Cancel in-progress upload | Upload stops immediately; no orphaned or partial files remain accessible in UI. | State Control |
| **FUNC-06** | Simultaneous multi-file upload / Drag & Drop batching | System handles multiple valid files smoothly (queues or processes concurrently) without freezing UI. | Usability |

---

## 2. Data Integrity & File Boundaries

| Test ID | Scenario Description | Expected Outcome | Risk Focus |
| :--- | :--- | :--- | :--- |
| **DATA-01** | Zero-byte file upload (`0 KB`) | System rejects empty file with an appropriate message ("File cannot be empty"). | Boundary Handling |
| **DATA-02** | Boundary test: 19.9 MB file upload | File uploads successfully within allowed limits. | Boundary Limit |
| **DATA-03** | Boundary test: Exact 20.0 MB file upload | File uploads successfully. | Boundary Limit |
| **DATA-04** | Boundary test: 20.1 MB & 50 MB file upload | System blocks upload client-side and server-side before full payload transmission. | Boundary Enforcement |
| **DATA-05** | File Checksum Verification (MD5 / SHA-256) | Hash of the file post-download matches the pre-upload hash exactly (no byte corruption). | Data Integrity |
| **DATA-06** | Special characters in filename (e.g., `contract_v1_#$&%_ñ.pdf`) | File uploads and preserves correct encoding without corrupting database or storage keys. | Encoding / Storage |
| **DATA-07** | Network loss mid-upload | System detects disconnection; partial files are cleaned up from temporary storage. | Data Leakage / Garbage Collection |

---

## 3. Security & Access Control

| Test ID | Scenario Description | Expected Outcome | Risk Focus |
| :--- | :--- | :--- | :--- |
| **SEC-01** | Single-owner isolation (User A vs User B) | Uploaded document is strictly visible and accessible only to the uploader (User A). | Access Control / Privacy |
| **SEC-02** | Direct Object Reference (IDOR) attempt | User B attempts to access User A's file via direct URL/API endpoint; system returns `403 Forbidden` or `404 Not Found`. | Authorization Bypass |
| **SEC-03** | Unauthenticated direct access | Accessing direct storage link (S3/blob URL) without an active session header is blocked. | Data Exposure |
| **SEC-04** | MIME-type spoofing / Magic Bytes validation | Executable (`.exe`) renamed to `.pdf` is detected via server-side file inspection and rejected. | Malware Injection |
| **SEC-05** | Malicious payload in filenames (XSS / Path Traversal) | Filenames containing `<script>` or `../../etc/passwd` are sanitized safely. | Script Injection / Traversal |
| **SEC-06** | Malware / Macro embedded in DOCX/PDF | System scans and neutralizes or rejects infected files before saving to persistent storage. | System Vulnerability |

---

## 4. Audit & Compliance Logging

| Test ID | Scenario Description | Expected Outcome | Risk Focus |
| :--- | :--- | :--- | :--- |
| **AUD-01** | Successful upload audit record | Audit log creates an entry with `Timestamp`, `User ID`, `File Name`, `File Size`, `IP Address`, and `Status: SUCCESS`. | Traceability |
| **AUD-02** | Failed upload audit record (Format/Size violation) | Audit log records failed attempts with detailed failure reason and `Status: FAILURE`. | Security Audit |
| **AUD-03** | Interrupted upload audit record | Audit log captures aborted/failed connection events accurately. | Completeness |
| **AUD-04** | Immutability of audit logs | Non-admin paralegal users cannot edit, modify, or delete audit entries. | Data Integrity / Compliance |
